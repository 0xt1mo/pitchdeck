AOS architecture

The Semantic Firewall.

The Semantic Intercept Fabric (SIF) goes beyond action-based policies to content-based controls with domain-specific ontologies — a Rust implementation with optimized search and rule algorithms. Each control is enforced at the kernel, below the agent.

The Semantic Intercept Fabric

Content-based controls with domain-specific ontologies, in three stages: a deterministic rule engine catches known patterns and zero-day injection vectors with dynamic rule updates; an ONNX-compatible ML detection layer (deploy your own model) handles anomaly detection; and a DLP scanner finds secrets, intellectual property, and PII by Named Entity Recognition. Sub-20ms enforcement — intent classified inline, enforced before the action executes.

WASM sandboxing

Agents execute within a WebAssembly isolated container. No direct access to the host OS. All plugins run as WASM capsules inside a sandboxed runtime.

IPC message bus

All external communication is routed through a monitored inter-process communication bus, enabling continuous, tamper-evident auditing.

Cryptographic agent identity

Every agent is assigned a revocable identity bound to a human principal. Eliminates static API keys. Map every active agent and its authorized scopes across the organization, and instantly quarantine rogue agents that deviate from baseline execution patterns.

Intelligent routing

Every agent request is scored before it runs and directed to the right model — by task complexity, cost, latency, and security clearance. Heavy work reaches strong models; trivial work never pays for them. Sensitive context is only ever routed to a target authorised to receive it. The routing decision is itself an inspected, recorded event.

Runaway compute & cost control

A poorly engineered agent stuck in a hallucination cycle can burn thousands in token costs. Hard rate limiting and token quotas are enforced at the kernel level before cost is incurred — the AOS Kernel blocks execution the instant a budget is reached. Human finance vs machine finance

The rails were built for humans, not machines.

Shared ledgers — the design under every chain from Bitcoin to the newest L2 — were built for humans: slow, sequential, contested. A single set of validators re-runs every transaction and agrees on one global order. That model fragments and contends the moment traffic arrives at machine scale.

Agents don’t work that way. They’re parallel, autonomous, and transacting at machine speed — an active agent may pay per data pull, per model call, per quote, thousands of times a second. The controls a financial institution already owns were built for the wrong actor: access control denies what a role can do, but an agent’s auth passes; detection fires after the agent has already acted; posture assumes a stable baseline an agent never holds between audits. The layer underneath the agent is the layer that has to come first.

Human finance · shared-ledger chains

Slow, sequential, contested. One validator set re-runs every transaction. Fragmentation by necessity, forced specialisation, complex smart-contract languages — and per-transaction fees that break agent micro-economics.

Machine finance · Unicity

Parallel, autonomous, at internet speed. Peer-to-peer settlement with unlimited throughput, fractions of a cent per transaction, chain- and asset-agnostic — one substrate the agent can transact across thousands of times a second.

Agent payments · x402

The agent pays per request — and the message is the payment.

x402 is the open standard that lets an AI agent pay for an API call inline — no checkout, no human, no wallet to set up. It revives HTTP status code 402 “Payment Required”: the agent requests data, the server answers 402, the agent attaches payment to the retry and gets its result. It is the rail for machine-speed finance — an agent paying per data pull, per model call, per quote, thousands of times a second.
